1 El problema y la misión

Un producto real ya en producción que hoy se opera a mano en un backoffice: un asesor avanza cada caso etapa por etapa. La misión es volver ese tramo agéntico de forma segura, sobre un sistema vivo.

2 Qué decide la IA y qué decide el código

Un falso OK (aprobar un expediente malo) cuesta mucho más que un falso rechazo. Por eso todo lo que mueve dinero o estado es código determinista.

🤖 La IA (propone)

  • Conversar y decidir la siguiente pregunta
  • Extraer campos de los documentos y clasificarlos
  • Redactar la corrección al cliente y el resumen al asesor
  • Elegir una acción dentro de la etapa, con lista blanca de tools

⚙️ El código (dispone)

  • Elegibilidad, perfil, cuotas, tasas y costo de la llave (Decimal)
  • Match de ingreso, nombre, domicilio, vigencias y aritmética
  • Transiciones de etapa y el gate «listo para financiera»
  • Permisos, idempotencia, versión y bitácora

6 El gate «listo para financiera»

7 Las seis decisiones técnicas del reto, en una línea

1 · ¿QUÉ ES UN «AGENTE» ACÁ?

Un operador de casos

Decide, por etapa, qué tool usar y qué preguntar. Resuelve operar el caso (casos que llegan completos sin retrabajo), no solo responder.

2 · TOOLS

Contrato + ejecutor único

Modelos Pydantic, permiso, etapas, riesgo e idempotencia. La misma capa sirve al asesor con otro principal: una sola bitácora.

3 · CONTEXTO Y ESTADO

El caso es la verdad

Agregado Case persistido con versión y esquema tipado. El agente recibe una proyección compacta sin datos personales; el chat no es el estado.

4 · DETERMINISMO VS IA

Dinero y estado = código

La IA extrae y conversa; el código compara con umbrales versionados. La confianza del modelo se cruza con validadores objetivos.

5 · GUARDRAILS Y HUMANO

Defensa en profundidad

Gate en la tool, sesión ligada a un caso, texto de documentos = dato, escalada con ticket y pausa; el asesor resuelve con justificación.

6 · OBSERVABILIDAD

Se mide, no se afirma

Bitácora de decisiones, make report y una evaluación adversarial que falla ante un solo falso OK.

8 Humano en el circuito

1 · Se escala

Inconsistencia grave, perfil dudoso, documento ajeno o texto sospechoso. El grafo se pausa.

2 · Ticket

Motivo, resumen, evidencia y acción sugerida en la bandeja del asesor.

3 · El asesor decide

Reanuda con justificación obligatoria, rechaza o declina. Un override queda auditado y no perdona la capacidad de pago.

4 · El agente retoma

Desde el checkpoint, o desde el caso persistido si el proceso se reinició.

  • Pila completa en Docker + prueba de humo HTTP + navegador

  • ≈ 3 conversaciones/s por proceso; con 10 en paralelo el p95 sube a 1,7 s (comparten el GIL)
  • Escalar exige mover sesiones a un almacén compartido

11 Lo que NO está hecho

  • Lector de documentos real (OCR / visión) y Buró real: son mocks (el reto lo permite).
  • Solo Azure OpenAI se probó con un modelo real; OpenAI directo, Gemini, DeepSeek y Anthropic solo contra transportes simulados.
  • Sesiones y límites en memoria de un proceso; datos personales sin cifrar en reposo; sin IaC, DAST ni trazas distribuidas.
  • Los umbrales (bandas, LTV, tasas, 35 %, tolerancias) son supuestos configurables, no cifras del producto.
  • El CI está escrito pero aún no se ejecutó en GitHub.

13 Cómo se usa

Tres formas, todas con los mismos 12 escenarios y sin claves: la interfaz visual (make start → http://localhost:8080), la terminal (make demo) o la API (/docs).

# con Docker: api + mocks + MongoDB + interfaz visual
make start → http://localhost:8080
make stop   # detener

# sin Docker ni red: los 12 escenarios
make demo
make demo ARGS="--scenario 09 --timeline"
# pruebas, evaluación adversarial y todo junto
make test
make eval  # falla ante un solo falso OK
make check

# probar con un modelo real (la clave no se guarda)
make smoke-llm ENV_FILE=… SCENARIO=09
